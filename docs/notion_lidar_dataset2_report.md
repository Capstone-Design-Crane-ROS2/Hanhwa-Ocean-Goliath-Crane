# LiDAR 객체 추정·추적 — 2차 ROSbag 검증 및 개선 실험 보고

> **한 줄 요약**: 2차 ROSbag(360° 단일 스캔)에서 LiDAR 스캔이 일부 버려지던 문제를 고쳐 모든 스캔이 객체 추정까지 전달되게 했고(생산 코드 반영), 평가 도구를 2차 GT 형식에 맞게 고쳐 S01–S09를 검증했다. GT 관측 1,514건을 모두 검출했고 ID Switch·Fragmentation은 0이다. 속도는 정상 이동 구간에서 정확하지만(p95 0.11–0.13 m/s, 사람) 발행 단계의 유효성 판정과 출발·정지 과도 구간에 문제가 있다. 속도 판정 개선(V4)과 객체 분리 개선(T8·C1·C1b·C1h·C2)은 **실험만 했고 생산 코드에는 적용하지 않았다.**

- 브랜치: `feature/lidar-dataset2-validation` (커밋 전)
- 근거 문서: `docs/report_step6_dataset2_merge.md`(스캔 전달), `docs/report_step7_dataset2_gt_eval.md`(GT 평가), `docs/report_step8_dataset2_velocity.md`(속도), `docs/report_step9_split_analysis.md`(객체 분리)

## 1. 작업 목표 및 담당 범위

**목표**: 새로 제공된 2차 ROSbag(10개 시나리오)으로 LiDAR 전처리 → 객체 추정 → ID 추적 → 속도 추정을 검증하고, 기존 로직에서 고칠 부분을 찾아 수정·실험한다.

**담당 범위**

| 포함 | 제외 (다른 팀원 담당) |
|---|---|
| LiDAR 360° 입력·전처리 연결 | S10 이동 크레인 상대 속도·TTC, 동적 위험 경계 |
| 객체 추정(클러스터링·위치·거리·박스) | S09 CAUTION 경고 지연·과경보 판단 |
| ID 추적, 속도 추정·유효성 판정 | ROS2 위험 판단 통합 검증, 위험 단계 정책 |
| GT 평가 도구 | Fusion·Camera 코드 |

S10은 동적 TF(`/tf_static` 없음)와 크레인 이동이 있어 상세 평가에서 제외했다(평가 도구는 이유를 출력하고 건너뜀).

## 4. 2차 LiDAR 입력 및 전처리 문제 해결 (생산 코드 반영)

**문제**: merge 노드는 카메라 프레임 시각(±2 ms)에 맞는 스캔만 출력한다. 2차 bag은 카메라 프레임이 군데군데 빠져 있어, 그 시각의 스캔이 **기록 없이 버려졌다**(S08 285개 중 47개, S09 211개 중 20개, S10 261개 중 22개). 버려진 스캔은 모두 GT 측정 구간이다.

**해결**: `lidar/lidar_merge_360.py`에 `camera_trigger` 파라미터 추가.
- 기본 `true`: 기존 동작 그대로(1차).
- `false`: `scan_offsets:=[0]`(단일 360° 스캔)일 때만 허용. 모든 스캔을 도착 즉시 원래 stamp·`frame_id`로 1번 발행하고, 카메라와 짝이 있는 스캔에만 기존 형식 `/lidar/merge_sync`를 발행(가짜 stamp 없음). 진단 카운트 `published`, `sync_published`, `scan_no_camera`, `camera_no_scan` 추가.
- LiDAR 평가 전용 설정 `config/lidar/dataset_20261122_lidar.yaml`(공용 `config/system/dataset_20261122.yaml` + `camera_trigger: false` 한 줄). **공용 설정·launch·위험 재생 설정은 바꾸지 않았다.**

**검증**

| 검증 | 결과 |
|---|---|
| 오프라인(bag 기록 순서, 2차 10개) | 출력 = bag 스캔 수(S08 238 → **285**, S09 191 → **211**, S10 239 → **261**), stamp 정확히 일치, 중복 0, `merge_sync`는 수정 전과 동일 |
| 1차 35개 회귀(기본값) | 출력 2,485프레임의 stamp·포인트·해시, `merge_sync`, 카운트 모두 수정 전과 동일 |
| ROS2 재생(LiDAR 체인만) | S08 285 / S09 211이 `/point_cloud_360` → ROI → voxel → ground → `/lidar/objects`까지 누락·중복 0. 1차 S7 478프레임 동일. 카메라 대기가 없어져 S09 지연 p50 97.9 → 77.5 ms |
| bag 자체 스캔 공백 | S08 6개, S10 1개(복구 불가, 추적기는 실제 시각 차를 사용) |

## 6. 속도 정확도 검증 및 주요 문제

**GT 속도**: 스캔당 GT 위치의 중앙 차분(실제 stamp 차)과 gt.json 경로 속도를 비교했다. 출발·정지가 차분 창에 걸리지 않는 프레임에서 둘의 차이는 0.000 m/s다(GT는 경로 모델과 정확히 일치). GT 출발·정지는 **순간 가감속**이라 실제보다 가혹한 조건이다.

**정상 이동 구간 칼만 속도 오차** (경로 속도 기준, m/s)

| 대상 | 프레임 | MAE | RMSE | p50 | p95 | 실제 발행 비율(이동 중) |
|---|---|---|---|---|---|---|
| S04 접근 사람 (1.2) | 131 | 0.053 | 0.067 | 0.041 | 0.123 | 43 % |
| S04 이탈 사람 (1.2) | 131 | 0.051 | 0.060 | 0.049 | 0.107 | **3 %** |
| S08 횡단 사람 (1.2) | 135 | 0.060 | 0.069 | 0.056 | 0.129 | 19 % |
| S09 지게차 (1.5) | 102 | 0.079 | 0.119 | 0.050 | 0.341 | 77 % |

(발행 비율은 출발·정지 창 프레임을 뺀 이동 프레임 140 / 140 / 162 / 111 기준.)

**칼만 / 판정 / 발행 구분**: 발행 속도 = 판정이 `unknown`이 아닐 때의 칼만 속도. S08·S09 재생 기록에서 발행값과 오프라인 칼만값의 차이는 p50 0.0004 m/s(같은 값)이다.

**주요 문제**

1. **걷는 사람 속도가 대부분 null**: 보폭 때문에 박스가 1 s 안에 0.47–0.63 m 변해 `shape_changing`(기준 0.5 m)이 42–70 % 프레임에서 걸린다. S04 이탈은 프레임 간 박스 급변 5회로 `shape_jump`가 46프레임 보류. 칼만 속도 자체는 정확하다.
2. **출발 직후 과소 속도**: 칼만이 순간 출발을 약 1 s 걸려 따라간다. S04 접근은 출발 직후 `stationary`(0.02–0.28)와 `moving`(0.35–0.87, GT 1.2)을 발행, S09는 재생 기준 출발 후 10프레임 전부 발행(오차 MAE 0.95).
3. **정지 직후 `moving` 유지**: S09는 정지 후 9프레임 `moving` 발행(칼만 1.52 → 0.47 m/s, GT 0).
4. **이동 방향 위치 지연**: 같은 위치·방향에서 이동 중과 정지 중을 비교하면 이동 중에만 진행 방향 뒤로 0.1–0.16 m(지게차 0.159 m ≈ 106 ms). 방위각에 따른 변화가 없어 "포인트별 회전 시각"보다는 "스캔 전체가 stamp보다 약 한 스캔 주기 이전"에 가깝지만, 시뮬레이터의 스캔·GT 시각 정의를 확인하지 않아 **원인 미확정**. 속도에는 영향 없음, 거리·TTC는 약 0.1 s 늦게 보임. **보정하지 않았다.**
5. 스캔 간격(bag 공백 200–300 ms)·클러스터 분리는 속도 오차와 무관했다.

## 7. 속도 유효성 개선 실험 결과 (적용 안 함)

실험 도구 `tools/exp_motion_validity.py`(생산 코드 변경 없음). LiDAR 객체에는 클래스가 없어 모든 후보는 크기·운동만 사용.

| 후보 | 내용 | 사람 발행 비율 | 잘못된 `moving`(오차 > 0.3) | GT 정지 중 `moving` | 판정 |
|---|---|---|---|---|---|
| V0 (현재) | – | 0.03–0.43 | 44 | 23 | 유지 |
| V1 | 형태 기준 0.5 → 0.8 m | 0.98–1.00 | 73 | 43 | 불가(잘못된 값 증가) |
| V2 | 형태 변화 "범위" → "추세" | 0.96–1.00 | 72 | 43 | 불가 |
| V3 | 0.4 s 짧은 창 속도와 칼만 불일치 시 보류 | 0.01–0.21 | 7 | 4 | 보수적 대안 |
| **V4** | V2 + V3 | **0.40–0.54** | **15** | **9** | **후보 보존(미적용)** |
| V6 / V7 | 칼만 가속 잡음 2 → 4 (± σ 기준 완화) | 0 / 0.03–0.42 | 0 / 21 | 0 / 7 | 불가(발행 없음 / ID Switch +3) |

(대상: 2차 S04 2명·S08·S09 + 1차 S7 트럭. 1차 S4·S1a·S7 정지 객체의 `moving` 오판은 모든 후보에서 0.)

**V4를 적용하지 않은 이유**: 정상 보행 구간의 약 절반을 여전히 보류하고(0.4 s 창의 보행 중심 흔들림), 창·문턱 값에 민감하며(0.5 s / 0.4 m/s에서는 잘못된 값이 V0 수준), 1차 전체 회귀·ROS2 재생 검증이 남았고, 시뮬레이션의 순간 가감속에 맞춘 값이다.

## 8. 객체 분리 오류 분석 및 개선 실험 결과 (적용 안 함)

**분리 지표**(`tools/eval_split_clusters.py`, 별도 결과 파일): 박스 안 포인트 ≥ 5이고 자기 포인트의 50 % 이상이 GT 박스 안인 클러스터를 후보로, 본체가 아닌 후보를 조각으로 센다. 조각 위치의 지속성(프레임 20 % 이상), 조각의 별도 확정 트랙, 본체↔조각 GT 매칭 교대, GT 간 병합을 기록한다.

## 11. 다른 팀원에게 공유할 사항

1. **2차 LiDAR 입력의 카메라 비의존 전환 영향**(LiDAR 전용 설정 사용 시만; 공용 설정·launch는 그대로 기존 동작)
   - Fusion: `/lidar/merge_sync`는 수정 전과 같아 `full`·`camera_only` 결과 불변 예상. 카메라 짝이 없는 스캔의 `/lidar/objects`는 짝 없는 LiDAR(`orphan_lidar`)로 집계·정리됨(에러 아님, 코드 주석은 "should not happen").
   - Risk: `/lidar/objects`가 약 8.9 → 10 Hz로 늘고, 추가 프레임에는 Fusion 라벨이 없음. 위험 평가 수치(경보 지연·과경보 프레임)가 달라질 수 있음.
   - 재생 중 카메라 메시지 전송 손실이 있음(S08 753 → 741 수신). 수정 전 동작에서는 그때 스캔도 버려짐.
2. **사람 속도가 `shape_changing`으로 자주 null**: 정상 보행 중 발행 3–43 %. 위험 판단에서는 "속도 불확실" 경로(8 m 규칙)로 처리될 가능성이 큼.
3. **S09 출발·정지 직후 부정확한 속도 발행**: 출발 직후 과소 속도(오차 약 0.95 m/s) 발행, 정지 후 9프레임 `moving`(칼만 1.52 → 0.47 m/s) 발행 → TTC가 정지 후에도 잠시 남을 수 있음.
4. **이동 객체 위치 약 0.1 s 지연**: 접근 객체가 실제보다 0.1–0.16 m 멀게(TTC 약 0.1 s 늦게) 보임. 원인 미확정, 보정하지 않음.
5. **클러스터 분리와 별도 트랙**: 소방차 지붕·승합차 지붕 등 차량 상부 조각이 별도 확정 트랙으로 나옴(크레인 경계 쪽에서 별도 객체로 보일 수 있음). 1차 빈 트럭·텔레핸들러는 본체↔조각 교대로 ID Switch.
6. 크레인 쪽 고정 구조물 5개는 2차 설정 제외 영역 안에 있으며 `excluded`로 표시됨.
7. 이 NUC에서는 ROS_DOMAIN_ID 11만 노드 간 통신이 되었음(61 등은 수신 0).

Fusion·Risk·TTC·위험 판단 정책 코드는 수정하지 않았다.
