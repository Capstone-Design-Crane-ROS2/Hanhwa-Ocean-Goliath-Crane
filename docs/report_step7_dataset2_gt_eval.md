# 2차 데이터셋 GT 기반 객체 추정·ID 추적 평가 (S01–S09)

> **요약**: 오프라인 평가 도구가 2차 GT(카메라 30 Hz 기준)로 같은 LiDAR 스캔을 최대 3번 평가하던 문제를 고쳐, 스캔당 GT 1개(`lidar_dt_s = 0` 우선, 아니면 `ground_truth_at_lidar`로 박스를 스캔 시각으로 이동)만 쓴다. 1차 대표 4개 bag의 결과는 수정 전과 완전히 같다. 2차 대표 6개 bag에서 GT 검출 100 %(관측 1,199건 전부 `ok`), 정지 사람 수평 오차 p50 0.01–0.05 m, ID Switch·Fragment 0이다. GT에 없는 클러스터(프레임당 5개)는 분석한 6개 bag 모두에서 같은 위치·크기인 **크레인 쪽(앞면 뒤 3–15 m, 지상 5.5–10 m) 고정 구조물**이며 전처리·클러스터링 오류가 아니다. 대형 차량 일부가 별도 조각 클러스터(소방차 지붕 등)로 나뉘어 추가 트랙이 생기는 사례가 있다.

작성: 2026-11-24(10절 이후 같은 날 추가: S02·S05·S07, ROS2 발행값, 분리 지표). 브랜치 `feature/lidar-dataset2-validation`. 객체 추정·클러스터링·추적·속도 코드는 변경하지 않았다.

## 7. 분리·병합과 ID Switch (1차 대표 bag, `--events`)

2차 대표 bag에는 ID Switch가 없어, 1차에서 Switch가 있는 2개 bag을 이벤트로 확인했다.

| bag / GT | Switch | 패턴 |
|---|---|---|
| S4 yaw 0° V_truck_01 (빈 트럭) | 4 | `split` 상태 전환 구간에서 발생(index 4, 11, 21: `ok → split`), 트랙 16 → 17 → 35 ↔ 36 |
| S4 yaw 0° V_truck_02 (빈 트럭) | 9 | 상태는 계속 `ok`. 트랙 24와 28이 번갈아 매칭(index 4, 9, 12, 13, 16, 19, 21, 27, 28) |
| S1a 텔레핸들러 | 11 | 상태는 계속 `ok`. 트랙 19와 22가 번갈아 매칭 |

- `ok`인데 Switch가 나는 경우는 **한 객체가 두 조각 클러스터로 나뉘고 각 조각이 자기 트랙을 안정적으로 유지**하며, 프레임마다 포인트가 더 많은 조각이 GT와 매칭되어 생긴다. 추적기가 ID를 잃는 것이 아니라 한 객체에 트랙이 2개 있는 상태다. 5.2의 2차 조각 사례와 같은 구조이며, 2차에서는 본체가 항상 우세해 Switch로 나타나지 않았다.
- 따라서 1차의 "클러스터 분리 변화 구간에서만 Switch" 결론은 `split` 상태만으로는 다 잡히지 않는다. 조각 클러스터(GT 박스 안 비매칭 클러스터)를 별도 지표로 세야 한다(4단계).

## 8. 전체 평가 전 확인 사항

1. **1차 35개 전체 회귀**: 수정 전 / 후 도구로 `eval_objects_gt`·`eval_tracking_gt`를 모두 돌려 비교. 대표 4개 기준 약 2.5분 → 35개 전체 약 45–60분(수정 전·후 2회).
2. **2차 나머지**: S02, S05, S07(정적) 객체·추적·비매칭 분석 약 2분. S10은 범위 밖(건너뜀 확인).
3. **발행값 기준 확인**: `config/lidar/dataset_20261122_lidar.yaml`로 S08·S09를 재생해 `tools/object_topic_monitor.py` 기록을 `eval_tracking_topics.py`로 비교(약 3분).
4. **결정 필요**: 조각 클러스터 지표(GT 박스 안 비매칭 클러스터 수·트랙 수)를 평가 도구 기본 출력에 추가할지(추가하면 1차 JSON에 새 키가 생김. 기존 키 값은 그대로).
5. 이동 방향 위치 지연(약 0.07–0.10 m)의 원인(스캔 stamp 정의)은 3단계에서 확인.

### 10.3 분리·병합 지표 (`tools/eval_split_clusters.py`)

기존 평가 JSON은 바꾸지 않고 별도 파일로 낸다. 같은 전처리·클러스터링·GT 매칭·추적기를 쓴다.

| 지표 | 정의 |
|---|---|
| 후보 클러스터 | GT 박스(여유 0.15 m) 안 포인트 ≥ `--min-points`(5) **그리고** 클러스터 자신의 포인트 중 박스 안 비율(purity) ≥ `--purity`(0.5). 박스를 지나가는 긴 구조물은 purity가 낮아 제외된다 |
| 본체 / 조각 | 본체 = 기존 GT 매칭 클러스터, 조각 = 본체가 아닌 후보 |
| clusters_per_frame | 관측 프레임별 후보 수 분포(0, 1, 2, 3+) |
| split_frame_ratio | 조각이 있는 프레임 / 관측 프레임 |
| fragment_point_share | 조각 프레임에서 박스 안 군집 포인트 중 조각 비율 |
| fragment_cells | 조각을 GT 박스 좌표(첫 변, 둘째 변, 높이) 0.5 m 격자로 묶음. 프레임 비율 ≥ `--persist`(0.2)이면 지속 조각, 아니면 일시 조각. 크기·바닥 높이·포인트·purity 중앙값 |
| fragment_track_ids | 조각에 붙은 확정 트랙 ID, 확정 트랙이 있던 프레임 수 |
| body_fragment_swaps | 본체의 트랙 ID가 **이전에 이 GT의 조각이 가졌던 ID로 바뀐 횟수**: GT 매칭이 다른 조각으로 넘어간 것(상태 `ok`인 ID Switch의 원인). 2026-11-24 4단계에서 프레임 수 → 변경 횟수로 정의 수정 |
| merged_events | 한 클러스터가 두 개 이상 GT 박스의 박스 내 포인트를 각각 ≥ `--merge-share`(0.3) 가진 경우 |

### 10.5 3단계(속도) 준비 사항

- GT 속도: 스캔당 1개로 정리된 LiDAR 시각 GT 중심의 중앙 차분(7.3절)과 `gt.json` 경로 속도 비교. 오프라인 로더에는 이미 반영되어 `eval_motion_gt.py`가 수정 없이 2차 스캔당 1개 GT를 쓴다(S10은 이 도구에서 아직 예외로 멈추므로 제외해서 실행).
